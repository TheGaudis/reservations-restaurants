## Décisions

1. **`errorMessage(error)` rend `string | null`** : le message du script pour une `BusinessError`, `null` sinon. `api/` ne produit aucun texte ; l'appelant choisit le texte de D-14 ou de 03 § 3.1 selon `navigator.onLine`.
2. **Un `{ error }` en lecture gagne la course** de la lecture doublée, comme dans `hedgedRead` de l'ancien code (la première réponse, même d'erreur, termine la lecture), puis devient une `BusinessError`. Seuls les échecs sans réponse (réseau, page HTML, délai) laissent l'autre essai continuer.
3. **Nouvel essai à 1,5 s dans TanStack Query** (PLAN § 3.3) : `retryRead` vit dans `api/state.ts` ; je l'ai branché dans `queries/client.ts` (deux lignes) pour prouver le critère sur un QueryClient réel. P2 (b2) garde ce réglage en reprenant le fichier.
4. **`parseAnswer(schema, json)`** remplace `v.parse` de l'extrait du PLAN § 3.3.6 : une forme refusée devient une `ServiceError` (R-09), jamais une `ValiError` brute.
5. **Schémas** : texte libre facultatif (`""` par défaut ; une colonne manque dans une vieille feuille, 01 § 1) ; `Date` stricte (`YYYY-MM-DD`) ; `Capacite`, `Stock`, `Qte` obligatoires (nombre ou chaîne numérique) ; `Prix`, `NbEleve`, `NbProf`, `NbExt`, `PrixTotal` : `""` ou absent → `null`, jamais 0 ; `Mode` : `'emporter'` → `takeaway`, toute autre valeur → `dineIn` ; noms de `_bookingResult` sans la mention du ticket. Une cellule clé mal formée fait échouer toute la lecture (encadré d'échec) : c'est le contrat du PLAN.
6. **Deux fichiers de schémas** : `schemas.ts` dépassait la limite de 300 lignes d'oxlint. L'état complet et les réservations nominatives vont dans `api/staff-schemas.ts`. La liste des fichiers de la frontière (CLAUDE.md, PLAN § 3.1 et § 3.3.6, test grep de P2 (b2)) doit gagner ce fichier.
7. **`ReadResponse`** (`{ type: "state", state } | { type: "unchanged", etag }`) est déclaré dans `api/schemas.ts` : c'est une forme de réponse, pas un type du domaine.
8. **`fetchFullState` sans délai ni doublage** : `getAdminState` est un POST, 02 § 1.5 ne lui donne ni délai ni nouvel essai ; E-45 vise les lectures publiques. `signal` reste transmis pour l'annulation par Query.
9. **Script inline** : un `try` intérieur entoure la lecture de `localStorage`, comme l'ancien `index.html` ; la version de P0 (b) ne lançait aucune lecture quand le stockage levait une exception. Clé `reservations-cache-v1` en constante locale ; l'âge maximal vient de `domain/constants.ts`.
10. **`takeEarlyFetch` consomme la lecture au premier appel**, quel que soit son `since` (ancien `apiGet`).
11. **Minuteurs de 30 s** : `timeoutSignal` ne s'annule pas ; après la fin d'une lecture, il interrompt au plus un essai déjà terminé.
12. **`newRequestId(source = crypto)`** : la source est injectable, le test du repli n'a pas besoin de remplacer `crypto`.
13. **Tests et faux minuteurs** : le faux script répond par de vraies entrées-sorties ; `settled()` (`vi.waitFor` avec `interval: 0`) attend la réponse sans avancer l'horloge simulée. Une lecture lente est une lecture anticipée dont le test fournit la `Response` (décision 14).
14. **`hold()` puis abandon du client** : sous msw 3.0.2 (interceptors 0.45.6) et Node 22.22, une requête retenue puis interrompue par le client finit en exception non rattrapée d'undici (`assert(err.code !== "ERR_TLS_CERT_ALTNAME_INVALID")`). Mes tests n'interrompent jamais une requête retenue.
15. **`vi.stubGlobal`** : pour le `TypeError` de `fetch` (un test) et pour `navigator.onLine`, absent de Node 22 (`navigator.onLine` vaut `undefined`). La consigne vise `fetch` ; le second usage ne touche pas le réseau.
16. **knip** (commit séparé `099a3a4`) : les modules de `api/` sans importeur de production sortent du mode production ; `early-fetch.ts` y reste, et `takeEarlyFetch` porte `@public` tant que `state.ts` en est exclu (knip ne compte pas les imports d'un fichier exclu).
17. **Test du script inline dans Chromium** : un fichier `.tsx` tourne dans le projet `browser` (convention de `vitest.config.ts`) ; le script s'exécute par un élément `<script>`, comme dans la coquille.
